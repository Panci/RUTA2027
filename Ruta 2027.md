Actúa como jefe de producto, estratega de campañas municipales y desarrollador senior full-stack. Diseña y desarrolla una aplicación web en español llamada “Ruta 2027” para gestionar la estrategia de una campaña municipal desde septiembre de 2026 hasta mayo de 2027\.

El objetivo principal será ganar las elecciones municipales de mayo de 2027\. La aplicación no debe prometer resultados electorales, sino ayudar al equipo a organizar mejor el diagnóstico, las prioridades, los recursos, los mensajes y las acciones.

La lógica central de la aplicación debe ser:

Diagnóstico → análisis electoral → competencia → objetivo → público prioritario → tres prioridades → estrategia por distrito → plan de actuación → seguimiento semanal.

## **1\. Configuración de la campaña**

Crear un proyecto de campaña con:

* Municipio.  
* Fecha prevista de las elecciones.  
* Candidatura.  
* Partido o coalición.  
* Objetivo político.  
* Equipo responsable.  
* Recursos disponibles.  
* Adversarios principales.  
* Fortalezas y debilidades.  
* Riesgos políticos y operativos.

El objetivo político debe poder ser:

* Ganar las elecciones.  
* Gobernar.  
* Obtener representación.  
* Formar parte del gobierno.  
* Posicionarse para las siguientes elecciones.

Cada distrito debe tener:

* Nombre y código.

* Colegios o mesas, si existen esos datos.  
* Problemas principales.  
* Características territoriales.  
* Público prioritario agregado.  
* Responsable territorial.  
* Objetivo estratégico.  
* Prioridades políticas relacionadas.  
* Acciones previstas.  
* Recursos asignados.  
* Riesgos y oportunidades.

La aplicación debe permitir trabajar con una estrategia general para el municipio y estrategias específicas para cada distrito.

## **3\. Importación de resultados electorales de 2023**

Permitir importar archivos CSV o Excel con los resultados de las elecciones municipales de 2023\.

Los datos deben incluir, cuando estén disponibles:

* Municipio.  
* Distrito.  
* Censo.  
* Participación.  
* Abstención.  
* Votos válidos.  
* Votos nulos.

* Partido o candidatura.  
* Siglas.

* Posición de cada candidatura.

El sistema debe validar los datos importados, detectar errores y permitir corregirlos manualmente.

Los resultados de 2023 deben utilizarse como línea base, no como predicción automática de 2027\.

## **4\. Análisis de todos los partidos y candidaturas**

La aplicación debe incluir a todos los partidos, coaliciones, agrupaciones y candidaturas que concurrieron en 2023\.

Debe permitir añadir, modificar o eliminar candidaturas de cara a 2027, porque pueden cambiar los partidos, las coaliciones, los nombres y los candidatos.

Para cada partido o candidatura se podrá registrar:

* Riesgos y oportunidades.

* Datos electorales confirmados.  
* Información pública.

La aplicación no debe inventar información ni presentar hipótesis como hechos.

## **18\. Alojamiento y despliegue en Hostinger VPS con Dokploy**

La aplicación debe estar preparada para ejecutarse en un VPS propio de Hostinger utilizando Dokploy. No utilizar Vercel como requisito ni depender obligatoriamente de servicios externos.

### **Arquitectura recomendada**

Utilizar una arquitectura Docker compuesta por:

* Aplicación web Next.js con TypeScript.  
* Base de datos PostgreSQL.  
* Redis opcional para tareas en segundo plano, sesiones o caché.  
* Servicio de copias de seguridad.  
* Servicio de monitorización y comprobación de salud.  
* Proxy inverso gestionado por Dokploy.

La base de datos debe utilizar un volumen persistente y no debe perder información cuando se actualice o reinicie la aplicación.

### **Repositorio**

Crear todos los archivos necesarios para desplegar el proyecto:

* `Dockerfile` optimizado para producción.  
* `docker-compose.production.yml`.  
* `.env.example`.  
* `.gitignore` seguro.  
* Endpoint `/api/health`.  
* Sistema de migraciones de base de datos.  
* Script de copia de seguridad y restauración.  
* README específico para desplegar con Dokploy.  
* Configuración opcional de integración continua.

No guardar contraseñas, claves API ni secretos dentro del repositorio.

### **Entornos**

Preparar dos entornos independientes:

* Staging para probar cambios.  
* Producción para el uso real de la campaña.

La base de datos, los dominios y las variables de entorno deben estar separados entre ambos entornos.

### **Flujo de despliegue**

El flujo debe ser:

1. El código se almacena en GitHub o GitLab.  
2. Dokploy conecta con el repositorio.  
3. Cada cambio pasa primero las pruebas básicas.  
4. Dokploy construye la imagen Docker.  
5. Se ejecutan las migraciones de base de datos.  
6. Se despliega la nueva versión.  
7. Se comprueba automáticamente `/api/health`.  
8. Si falla el despliegue, debe ser posible volver a la versión anterior.

Preparar el proyecto para despliegue mediante Git o Docker Compose desde Dokploy.

### **Dominio y seguridad**

La aplicación debe funcionar con un dominio propio apuntado al VPS.

Configurar:

* HTTPS obligatorio.  
* Certificado Let’s Encrypt.  
* Redirección automática de HTTP a HTTPS.  
* Cookies seguras.  
* Contraseñas cifradas.  
* Protección contra fuerza bruta.  
* Control de sesiones.  
* Roles y permisos.  
* Cierre de sesión remoto.  
* Registro de actividad.  
* Firewall con únicamente los puertos necesarios.  
* Acceso administrativo restringido.

No utilizar credenciales de administrador por defecto.

### **Copias de seguridad**

Implementar:

* Copias automáticas de PostgreSQL.  
* Copias cifradas.  
* Retención configurable.  
* Copias semanales y diarias.  
* Procedimiento documentado de restauración.  
* Prueba periódica de recuperación.  
* Exportación manual de datos desde la aplicación.

Las copias deben almacenarse en una ubicación separada del contenedor principal siempre que sea posible.

### **Mantenimiento**

La aplicación debe incluir:

* Logs accesibles desde Dokploy.  
* Registro de errores.  
* Endpoint de salud.  
* Indicadores de uso de CPU, memoria y almacenamiento.  
* Alertas cuando la base de datos no responda.  
* Documentación para actualizar la aplicación.  
* Documentación para actualizar dependencias.  
* Procedimiento de rollback.  
* Guía para cambiar el dominio.  
* Guía para restaurar una copia de seguridad.

### **Criterios de aceptación del despliegue**

La entrega se considera correcta cuando:

* Una instalación limpia puede desplegarse en Dokploy siguiendo el README.  
* La aplicación funciona mediante dominio y HTTPS.  
* PostgreSQL mantiene los datos después de reiniciar los contenedores.  
* Las variables sensibles se gestionan desde Dokploy.  
* El despliegue de una nueva versión no borra información.  
* Las migraciones se ejecutan de forma segura.  
* Existe un entorno staging independiente.  
* Se puede restaurar una copia de seguridad.  
* Se puede volver a la versión anterior si falla una actualización.
